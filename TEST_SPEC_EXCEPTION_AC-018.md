# AC-018: terminal commitment and output transport

Status: **APPLIED CLARIFICATION, 2026-10-17**. Locked AC-018, REL-002 and TH-015 remain authoritative; all six locked file hashes are unchanged. The explicit disposition below selects the final successful-response cancellation decision as terminal commitment. Actual observation, independent recorded-evidence inspection and current output-cap/cancellation checks support this disposition. The machine-readable association is in [the clarification record](spec/ac018-clarification.json). This does not establish full release readiness.

AC-018 requires one failure object and no partial success when cancellation occurs before final publication. TH-015 requires checking cancellation before publication and prohibits a partial-success streaming protocol. The text does not identify whether final publication means selecting the terminal response, the first visible byte, or completion of transport. A stdout byte stream cannot retract bytes already delivered to a reader.

The precise boundary is the final atomic cancellation decision on the successful-response path, after execution, complete result collection, output-cap checks and complete serialization. A cancellation flag set before that decision selects one E_CANCELLED object and exit 4. A false flag commits the complete successful envelope. Sending SIGINT or SIGTERM does not itself establish that its handler has set the flag before this decision. A racing request may receive the already-committed success even while stdout is still empty. Earlier typed failures bypass this success-path conversion; this clarification gives cancellation no new precedence over an already selected error. No result rows are streamed during query execution. The selected response is one logical terminal JSON object; write_all and the separately written newline provide no atomic-write or atomic-delivery guarantee.

This clarification adds no query feature and changes no limit, tenant rule, error code, row/bag/NULL semantics, or result cap. It clarifies the cancellation race and the existing API's transport limitation. Exit 0 means output writes completed successfully from the process perspective, not that a reader parsed, persisted or acknowledged the response. A caller must reject incomplete JSON and treat exit 6 as failure even if a visible prefix contains status ok. If the output channel fails or closes, delivery may be truncated or absent and exit 6 reports transport failure; a failed channel cannot guarantee a replacement error. Hard process termination likewise cannot guarantee an envelope. Neither event is a successful query or cooperative E_CANCELLED observation.

The independent source inspections found that choosing this boundary requires explicit disposition; a test expecting success after this decision cannot establish the locked wording by itself. Earlier actual shared-Linux observations delivered SIGINT after a visible response prefix, then drained one complete success; closing the reader produced exit 6. Those facts concern transport already in progress. They do not discriminate a pre-publication boundary or establish AC-018 compliance.

The unchanged-Rust GDB experiment now has five actual Linux observations: no-signal and both sides of the decision for SIGINT and SIGTERM, all with stdout empty at the controlled stop. Both signals retain rt_sigreturn syscall-entry observations after their handlers run. Pre-decision cases emitted only E_CANCELLED/exit 4; post-decision and no-signal cases emitted the complete independently specified authorized row [[7]]/exit 0. Independent inspection of the actual full disassembly places the pre-stop before the atomic load and the post-stop after the decision, before response dispatch/stdout. No debugger flag patch or product hook changes this build. A separate actual mutation bypassed only the final E_CANCELLED conversion, retained both source anchors, failed specifically on wrong success/exit 0 after handled cancellation, then restored PASS and original source/binary identities.
