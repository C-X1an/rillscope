# AC-018: terminal commitment and output transport

Status: **DRAFT CLARIFICATION, NOT APPLIED**. Locked AC-018, REL-002 and TH-015 remain authoritative. This document does not establish acceptance or change a locked file/hash. Independent review and actual boundary observations remain required before disposition. The current experiment is observational and cannot approve its own interpretation.

AC-018 requires one failure object and no partial success when cancellation occurs before final publication. TH-015 requires checking cancellation before publication and prohibits a partial-success streaming protocol. The text does not identify whether final publication means selecting the terminal response, the first visible byte, or completion of transport. A stdout byte stream cannot retract bytes already delivered to a reader.

The proposed precise boundary is the final atomic cancellation decision on the successful-response path, after execution, complete result collection, output-cap checks and complete serialization. A cancellation flag set before that decision selects one E_CANCELLED object and exit 4. A false flag commits the complete successful envelope. Sending SIGINT or SIGTERM does not itself establish that its handler has set the flag before this decision. A racing request may receive the already-committed success even while stdout is still empty. Earlier typed failures bypass this success-path conversion; this clarification gives cancellation no new precedence over an already selected error. No result rows are streamed during query execution. The selected response is one logical terminal JSON object; write_all and the separately written newline provide no atomic-write or atomic-delivery guarantee.

This proposal adds no query feature and changes no limit, tenant rule, error code, row/bag/NULL semantics, or result cap. It clarifies the cancellation race and the existing API's transport limitation. Exit 0 means output writes completed successfully from the process perspective, not that a reader parsed, persisted or acknowledged the response. A caller must reject incomplete JSON and treat exit 6 as failure even if a visible prefix contains status ok. If the output channel fails or closes, delivery may be truncated or absent and exit 6 reports transport failure; a failed channel cannot guarantee a replacement error. Hard process termination likewise cannot guarantee an envelope. Neither event is a successful query or cooperative E_CANCELLED observation.

The independent source inspections found that choosing this boundary requires explicit disposition; a test expecting success after this decision cannot establish the locked wording by itself. Earlier actual shared-Linux observations delivered SIGINT after a visible response prefix, then drained one complete success; closing the reader produced exit 6. Those facts concern transport already in progress. They do not discriminate a pre-publication boundary or establish AC-018 compliance.

The added unchanged-binary GDB experiment stops before and after the final flag decision with stdout still empty. It delivers real SIGINT and observes handler return before resuming. Its no-signal control expects the independently specified authorized row. The pre-decision case expects only E_CANCELLED/exit 4; the post-decision case records whether the selected success/exit 0 is delivered. Raw diagnostic output, binary/source identities and all failures are retained separately. No debugger flag patch or product hook changes the tested binary.

Requiring cancellation through the last transmitted byte would require a separately designed transactional/framed acknowledgement protocol. This proposal does not silently introduce that API or call it implemented. Final disposition must state the selected interpretation, evidence, independent assessment and remaining transport risk. Until then AC-018 final closure remains NOT RUN.
